Evidence Options

What session evidence gets committed to the repo alongside memories, and how much of the OptChat gist do we actually build?

Memories are the product (decision 0004). Evidence is what a memory links back to when an agent needs the full story. This choice sets repo growth, harness coverage, cost, and how big v1 is.

The gist's mechanisms vs. what we've proposed

The OptChat gist is built on one promise: nothing is ever lost. Every message is kept verbatim, and a summary tree makes it navigable. Here is each piece of it, what the current proposal (Option B) does with it, and which options bring it back.

The trade in one line: the gist optimizes for one person never losing anything. We are optimizing for a team getting the right slice of knowledge. The options below differ in how much of "never losing anything" we pay to keep.

Research, 2026-10-20

What research changed

Copilot does expose sessions. VS Code (preview), Copilot CLI and Claude Code all pass hooks a transcript path. The coding agent runs hooks too.
But every format is "unstable". All three vendors say transcript files may change. Safer: build our own event log from hook fields (prompt, tool, args, result), close to the gist's log.
One hook location for Copilot. .github/hooks/*.json is read by VS Code, the CLI and the coding agent. Claude Code needs its own config.
Local transcripts expire. Claude Code deletes its own transcripts after 30 days by default. "Keep it local" only lasts if we write our own copy.
GitHub Models is retired (July 2026). A background summarizer needs a model API key, or Copilot CLI in Actions billed in AI Credits.
Repo size guidance: ideally under 1 GB, strongly advised under 5 GB. Git LFS: 10 GiB free, 250 GiB on Team plans.

Full sources: docs/research/2026-10-20-harness-capabilities.md.

Detail

The five options

A

Links only

Memories carry links to the commit and PR they came from. No other evidence. "Zoom" means opening the diff and PR discussion.

CommittedMemory files with evidence: [commit, PR]
Local onlyNothing
Gist keptAlmost none of the evidence side

Pros

  • Smallest possible; nothing new to capture
  • Works identically in every harness, including the coding agent
  • No secrets risk beyond what's already in the code

Cons

  • The conversation's reasoning ("why") is lost unless the memory itself captures it
  • PRs often say little about why; legacy lessons get thin
  • Doubtful memories can't be checked, which matters more now that memories aren't reviewed one by one (0009)

Scope impact

No capture work beyond drafting. Removes evidence from the design almost entirely. Weakest fit for "the why behind decisions".

B

Excerpts inside each memory

Current proposal (agent call)

When the agent drafts a memory, it includes short verbatim excerpts: the user's exact words, the exact error, the key line of output. Capped at about 1–2 KB per memory, plus commit/PR links.

CommittedMemory files with an ## Evidence section of quotes
Local onlyOptional: our own event log from hooks, not committed
Gist keptUser's words first; zoom to source (one level)

Pros

  • Keeps the "why" in the user's own words, right where it's needed
  • Works in every harness: the agent supplies excerpts through memory_draft, no transcript parsing
  • Tiny: decades before repo size matters
  • No summarizer, no model API key, no background jobs
  • Agents pick what's relevant, so secrets are rarely copied (and can be scanned)

Cons

  • Lossy: anything the agent didn't excerpt is gone for teammates
  • Excerpt quality depends on the drafting prompt and the model
  • Breaks the gist's core promise that nothing is ever lost
  • Can't answer questions nobody thought to save a memory about

Scope impact

Adds: an evidence section to the memory format, excerpt validation and size caps, secret scanning of memory files. The summary tree, compactor and transcript capture all move out of v1.

C

Excerpts + committed session summary trees

Everything in B, plus each session's gist-style 512-byte summary tree committed to the repo. Teammates can zoom from a memory into the summaries of the session it came from, but not to raw messages.

CommittedB + .memory/sessions/<author>/<id>.tree.jsonl
Local onlyRaw event log
Gist keptSummary tree, compaction, multi-level zoom

Pros

  • Much richer context for "how did we get here?"
  • Recovers detail nobody thought to save a memory about
  • The closest faithful use of the gist that's still a reasonable size
  • One file per session, so still conflict-free

Cons

  • Needs a summarizer: ≈2 cheap-model calls per logged event, about 3 million a year for the team. Needs a model API key, or Copilot CLI in Actions using AI Credits
  • Needs capture hooks in every harness (VS Code hooks are preview; formats are unstable)
  • Summaries copy ids, paths and errors exactly, so they can copy secrets too
  • Hundreds of MB a year in permanent history

Scope impact

Adds: hook adapters (.github/hooks + Claude config), a normalized event log, a compactor (prompt, ruler, retries, queues, parallelism), a model dependency and cost, a tree format, multi-level zoom, and a secret scan of summaries. Roughly doubles v1.

D

The full gist: raw logs + trees committed

Everything in C, plus the raw event log (tool output clipped) committed. Nothing is lost for anyone on the team.

CommittedC + .memory/sessions/<author>/<id>.log.jsonl
Local onlyNothing extra
Gist keptAll of it, except the view and cache design

Pros

  • Keeps the gist's promise: zoom all the way to the verbatim message
  • Maximum material for future audits and evals
  • Nothing depends on the agent choosing what to save

Cons

  • ≈1–3 GB a year: past GitHub's 1 GB guidance within about a year, permanently, in every clone
  • Highest secret risk: raw tool output includes env vars and tokens
  • Slower clones and fetches for everyone, including CI
  • Removing it later means rewriting history for the whole team

Scope impact

Everything in C, plus strict secret scanning of raw logs, clipping rules, a repo-size management plan, and likely a migration later. The largest scope, and the one most likely to hit the anti-goal "it becomes a chore".

E

Excerpts in the repo, sessions in a separate store

B in the code branch. Session trees (C) or full logs (D) go somewhere that doesn't bloat code history: an orphan branch such as memory-evidence, Git LFS, or a separate evidence repo. Memories reference sessions by id; the tool fetches them on demand.

Committed to code branchB only
Separate storeSession trees and/or raw logs
Gist keptAs much as C or D, without the repo cost

Pros

  • Code repo stays lean; clones stay fast
  • Teammates can still zoom into each other's sessions
  • The evidence store can be pruned or rewritten without touching code history
  • Can be added later on top of B without changing the memory format

Cons

  • Still needs the summarizer and capture hooks from C
  • Evidence is no longer branch-aware: it lives in one shared, append-only store
  • Extra plumbing: syncing an orphan branch, LFS quotas (10 GiB free), or a second repo's access
  • "Pull a branch, get its memories" holds for memories, but evidence needs a separate fetch

Scope impact

C's or D's scope, plus storage plumbing and on-demand fetch in memory_zoom. Best treated as a later phase, not v1.

Proposed (agent call)

Suggested path: B now, keep the door open to E

v1

Option B. Excerpts inside memories. No summarizer, works in every harness, tiny. Memory format reserves evidence: references so session ids can be added later without changing anything.

v1, optional

Local event log. Hooks write our own normalized log (the gist's log format) to a gitignored folder. Costs little, survives Claude Code's 30-day cleanup, and gives real data for the next step.

after evals

Measure. Use the retrieval eval set. If agents keep missing context that excerpts didn't keep, that's the evidence for richer evidence.

v2, if needed

Option E with session trees. Add the gist's compactor and push session trees to a separate store. The local logs from v1 can be backfilled.

Why: it keeps v1 small and harness-agnostic, avoids a permanent repo-size decision, and defers the costliest work (summarizer, hooks everywhere) until data shows it's needed. Cost: teammates can't zoom into each other's full sessions in v1.

Open

Questions that decide it

  1. Is "nothing is ever lost, for the whole team" a requirement or a nice-to-have? If it's a requirement, only D or E (with full logs) qualify.
  2. Must teammates be able to zoom into each other's sessions? If yes, C or E. If excerpts are enough, B.
  3. Who pays for summarization, and how? A model API key per team, or Copilot CLI in GitHub Actions billed in AI Credits. Options C, D and E all need one.
  4. How much repo growth is acceptable? Megabytes (A, B), hundreds of MB a year (C), or gigabytes (D).
